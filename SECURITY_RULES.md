# SECURITY_RULES.md — Premissas Irrestritas de Segurança do Projeto

Este documento é a **política de segurança permanente** do projeto Krona Express.

As regras abaixo são **obrigatórias, irrestritas e não negociáveis**. Devem ser
respeitadas em qualquer:

- alteração de código;
- criação de arquivo;
- instalação de dependência;
- refatoração;
- commit;
- push;
- Pull Request;
- merge;
- configuração;
- build;
- deploy;
- implementação futura de backend, API, autenticação ou banco de dados.

Nenhuma funcionalidade, prazo, solicitação ou facilidade de desenvolvimento pode
justificar a violação destas regras.

Caso alguma solicitação futura entre em conflito com estas premissas, **não
contorne a regra**: sinalize o conflito e proponha uma alternativa segura.

Estas regras têm **precedência** sobre solicitações de implementação que possam
reduzir a segurança do projeto. Nunca alterar, remover, flexibilizar ou ignorar
este arquivo sem **autorização humana explícita**.

---

## 1. Segredos e variáveis de ambiente

É terminantemente proibido versionar qualquer segredo ou credencial.

Nunca adicionar ao Git:

- `.env`, `.env.local`, `.env.development`, `.env.production`, `.env.test`, `.env.*.local`;
- senhas, tokens, API Keys privadas, Client Secrets, Private Keys;
- certificados privados;
- connection strings contendo credenciais;
- cookies de sessão, tokens de autenticação;
- credenciais de banco, de cloud, do GitHub, de deploy;
- secrets de serviços externos.

Todos os arquivos `.env*` reais devem permanecer protegidos pelo `.gitignore`.

A **única exceção** permitida é `.env.example`, que deve conter somente nomes das
variáveis e valores fictícios ou vazios. Jamais copiar valores reais para
`.env.example`.

## 2. Regra específica para Next.js

Qualquer variável com prefixo `NEXT_PUBLIC_` deve ser considerada **100% pública**.

Nunca utilizar `NEXT_PUBLIC_*` para senhas, tokens privados, credenciais,
connection strings, API Keys privadas, secrets ou informações internas sensíveis.

Nenhum segredo pode chegar ao Client Component, ao bundle JavaScript, ao HTML ou
ao código executado no navegador. Não utilizar configurações que incorporem
secrets no bundle do frontend. Tudo que for sensível deve permanecer
exclusivamente no ambiente server-side/backend.

## 3. Segredos fora do `.env`

É proibido inserir credenciais ou informações sensíveis reais em qualquer arquivo,
incluindo `.ts`, `.tsx`, `.js`, `.jsx`, `.json`, `.yaml`, `.yml`, `.md`, README,
testes, mocks, fixtures, scripts, documentação, comentários, logs, screenshots,
configurações de IDE, workflows de CI/CD, exemplos de código e arquivos
temporários.

Nunca utilizar segredo real, nem mesmo como exemplo temporário.

## 4. Segredos no histórico Git

Antes de qualquer commit ou push, verificar se existe informação sensível sendo
adicionada.

Se um segredo tiver sido commitado anteriormente, mesmo que removido do arquivo
atual, considerá-lo **comprometido** por permanecer no histórico. Nesse cenário:

1. sinalizar imediatamente;
2. considerar a credencial comprometida;
3. recomendar sua rotação/substituição;
4. identificar onde ela aparece;
5. avaliar a necessidade de remoção do histórico Git;
6. validar novamente o histórico após a correção.

A simples exclusão do arquivo atual **não** é correção suficiente.

## 5. `.gitignore` obrigatório

Manter o `.gitignore` atualizado durante todo o projeto. No mínimo, quando
aplicável, ignorar:

```gitignore
.env
.env.*
.env.local
.env.*.local

.next/
node_modules/
coverage/
dist/
build/

*.log

*.pem
*.key
*.pfx
*.p12

*.bak
*.backup
*.dump
```

Também ignorar caches, arquivos temporários, arquivos locais de IDE que não devam
ser compartilhados, certificados privados, chaves privadas, dumps de banco,
backups e artefatos locais.

O `.env.example` pode ser versionado desde que não contenha nenhum dado real.

## 6. IA — proibição absoluta de autoria/coautoria no repositório

Nenhuma IA (incluindo assistentes de código) pode aparecer como autor, coautor,
participante, colaborador ou identificador deste projeto.

É terminantemente proibido manter ou adicionar:

- `Co-Authored-By` relacionado a qualquer IA;
- IA como participante ou colaborador de commit ou Pull Request;
- autoria, assinatura ou trailers de commit relacionados a IA;
- textos como `Generated by`, `Generated with`, `Created with AI`, `Created by AI`;
- referências a provedores de IA como geradores do código;
- badges, ícones, logos, imagens ou identificadores visuais de ferramentas de IA;
- arquivos ou links promocionais relacionados a ferramentas de IA;
- comentários ou metadata indicando geração por IA.

A proibição vale para arquivos atuais e novos, commits futuros e antigos (inclusive
o primeiro commit), todo o histórico Git, branches, PRs, documentação, README e
configurações do projeto.

> Observação: a menção a nomes de ferramentas de IA **neste arquivo de política**
> e no `CLAUDE.md` existe apenas para definir a proibição. Isso não constitui
> atribuição de autoria.

## 7. Reescrita de histórico para remover IA (exceção controlada)

Se for necessário reescrever o histórico Git **especificamente** para eliminar
referências, autoria, coautoria ou metadata de IA, essa reescrita está autorizada
como exceção controlada à regra geral de não alterar histórico.

A correção deve preservar: conteúdo funcional legítimo do projeto, autoria humana
legítima, estrutura do projeto, branches relevantes, código existente e o
histórico funcional na medida do possível.

Nunca atribuir artificialmente um commit de IA a uma pessoa aleatória. Utilizar
somente a autoria humana legítima já existente ou definida para o projeto.

Após qualquer reescrita, realizar nova auditoria completa.

## 8. Regra permanente para novos commits

Nenhum novo commit pode conter qualquer identificação, assinatura, participação ou
coautoria de IA.

Antes de criar commits, verificar a existência de termos como `Claude`,
`Anthropic`, `Co-Authored-By`, `Generated by`, `Generated with`,
`Created with AI`, `Created by AI` ou equivalentes.

Assistentes de IA não devem adicionar automaticamente trailers de coautoria. Se
existir configuração, hook, script, plugin ou ferramenta adicionando esse
comportamento, ele deve ser identificado e desativado. Neste projeto isso é
imposto por `.claude/settings.json` (`includeCoAuthoredBy: false`).

## 9. Commits e Pull Requests

Nunca incluir em commits ou PRs: segredos, credenciais, `.env`, tokens, logs
sensíveis, dumps, arquivos temporários, backups, artefatos locais, arquivos
desnecessários, referências a IA, coautoria de IA ou badges/ícones de IA.

Antes de qualquer commit relevante, revisar `git status` e `git diff` (e os
arquivos staged quando necessário). Nunca executar `git add .` de forma cega sem
verificar previamente o que será incluído.

## 10. Branch principal

Nunca realizar force push na branch principal sem necessidade explícita,
sobrescrever histórico sem justificativa, remover proteção de branch, ignorar
verificações de segurança ou desabilitar validações para permitir merge.

A exceção de reescrita de histórico para remover IA deve ser realizada de forma
controlada e exclusivamente para essa finalidade.

Quando houver fluxo colaborativo, utilizar proteção de branch e revisão por Pull
Request.

## 11. Dependências npm

Não instalar bibliotecas sem necessidade real. Antes de adicionar uma dependência,
verificar: finalidade, manutenção, reputação, vulnerabilidades conhecidas. Evitar
pacotes abandonados, desconhecidos ou duplicados, e verificar se a funcionalidade
já existe no projeto. Preferir bibliotecas amplamente utilizadas e mantidas.

## 12. Lockfile

Manter versionado o lockfile do gerenciador de pacotes (`pnpm-lock.yaml`). Nunca
excluir ou recriar o lockfile apenas para esconder conflitos ou vulnerabilidades.
Alterações inesperadas no lockfile devem ser analisadas antes do commit.

## 13. Vulnerabilidades de dependências

Alertas de segurança críticos ou altos não devem ser ignorados silenciosamente.
Nunca usar `--force` apenas para fazer instalação ou build funcionar sem
compreender as consequências. Não reduzir versões, ignorar warnings ou remover
verificações apenas para contornar problemas. Se uma correção provocar breaking
change, apresentar o impacto antes de alterar a arquitetura.

## 14. Frontend não é ambiente confiável

Tudo que é enviado ao navegador deve ser considerado acessível e manipulável pelo
usuário. Nunca confiar exclusivamente no frontend para proteger permissões, roles,
perfis, autorização, regras críticas, credenciais, dados privados ou cálculos
sensíveis. Ocultar botão, menu, rota ou componente não é controle de acesso real.
Quando houver backend, toda autorização crítica deve ser revalidada no servidor.

## 15. Autenticação e autorização futuras

Frontend = interface e experiência. Backend = autoridade.

Nunca implementar segurança real baseada apenas em verificações no navegador (ex.:
`if (role === "admin")`). O backend deve validar identidade, sessão, autenticação,
autorização, perfil e acesso ao recurso solicitado. Nunca considerar valores
enviados pelo cliente como confiáveis.

## 16. Tokens e sessões

Quando houver autenticação, evitar armazenar tokens sensíveis permanentemente em
`localStorage`, `sessionStorage`, IndexedDB ou variáveis globais do browser. Não
criar autenticação improvisada. Cookies sensíveis devem considerar `HttpOnly`,
`Secure` e `SameSite`.

## 17. XSS e execução de código

Não utilizar sem justificativa técnica e tratamento apropriado: `eval()`,
`new Function()`, execução arbitrária de JavaScript, `innerHTML`,
`dangerouslySetInnerHTML` ou construção de código executável a partir de dados
externos. Todo dado de usuário, URL, API, arquivo ou serviço externo é não
confiável.

## 18. Validação de entradas

Assumir que entradas do usuário são potencialmente maliciosas ou inválidas.
Validar, quando aplicável: tamanho, formato, tipo, valores permitidos, campos
obrigatórios, URLs, números, datas, arquivos e extensões. Validação frontend nunca
substitui validação backend.

## 19. Uploads futuros

Nunca confiar somente em nome do arquivo, extensão ou MIME informado pelo
navegador. Deverão existir validações server-side para tamanho, tipo, conteúdo,
extensão, permissões, destino e nome seguro. Arquivos enviados pelo usuário nunca
devem ser executados diretamente.

## 20. Logs e console

Nunca registrar em logs: senha, token, cookie, secret, Authorization Header,
credenciais, connection strings, informações sensíveis ou o conteúdo completo de
`process.env`. Nunca usar `console.log(process.env)`. `console.log` temporários
devem ser revisados antes de commits destinados à produção.

## 21. Mensagens de erro

Nunca expor ao usuário final stack traces, caminhos internos, infraestrutura,
queries, tokens, segredos, detalhes de banco de dados, connection strings ou
variáveis de ambiente. Mensagens ao usuário devem ser controladas e sanitizadas.

## 22. URLs e redirecionamentos

Não permitir redirecionamento arbitrário fornecido pelo usuário sem validação.
URLs externas devem ser verificadas. Evitar esquemas potencialmente perigosos.
Links externos em nova aba devem usar as proteções adequadas
(`rel="noopener noreferrer"`).

## 23. Headers de segurança

Ao preparar a aplicação para publicação, avaliar e configurar corretamente:
`Content-Security-Policy`, `X-Content-Type-Options`, `Referrer-Policy`,
`Permissions-Policy`, `frame-ancestors` e `Strict-Transport-Security` quando
aplicável. Não criar políticas excessivamente permissivas apenas para fazer
funcionalidades funcionarem.

## 24. CORS

Quando houver backend/API, nunca usar CORS irrestrito em produção sem necessidade
técnica comprovada. Evitar `Access-Control-Allow-Origin: *` em endpoints
autenticados ou sensíveis. Permitir somente as origens necessárias.

## 25. CSRF

Quando houver autenticação baseada em cookies e endpoints que alterem dados,
avaliar e implementar proteção contra CSRF. Não assumir que uma única configuração
resolve todos os cenários.

## 26. Dados sensíveis

Nunca utilizar dados sensíveis reais em mocks, fixtures, testes, exemplos,
screenshots, documentação ou demonstrações. Utilizar dados fictícios ou
corretamente anonimizados.

## 27. Build de produção

Antes de disponibilizar builds de produção, verificar se os artefatos não expõem
source maps desnecessários, arquivos internos, configurações, backups, arquivos
temporários, segredos, informações de infraestrutura ou conteúdo de
desenvolvimento. Não publicar arquivos desnecessários ao funcionamento da
aplicação.

## 28. CI/CD e GitHub Actions

Nunca escrever secrets diretamente em arquivos YAML. Utilizar os mecanismos de
Secrets, Variables e environments da plataforma. Nunca imprimir secrets no
console. Aplicar o princípio de menor privilégio às permissões dos workflows. Não
conceder escrita quando somente leitura for necessária. Não executar código não
confiável com acesso a secrets. Actions e dependências externas devem ser
avaliadas antes do uso.

## 29. Proteções do GitHub

Quando disponíveis, recomendar e manter habilitados: Secret Scanning, Push
Protection, Dependabot Alerts, Dependency Review, proteção da branch principal e
revisão obrigatória quando aplicável. Essas proteções não substituem revisão
manual.

## 30. Configuração pública x segredo

Nem toda configuração precisa ser privada; é permitido versionar configurações
públicas necessárias ao frontend. Entretanto, qualquer informação que conceda
acesso, autentique, autorize, permita operação privilegiada, revele credencial ou
revele infraestrutura sensível deve ser tratada como privada. Na dúvida,
considerar segredo até validação.

## 31. Nunca enfraquecer segurança para "fazer funcionar"

É proibido resolver problemas por: desativação de validações; bypass de
autenticação ou autorização; CORS totalmente aberto; exposição de secrets; remoção
de controles; desativação silenciosa de segurança; desativação de SSL/TLS sem
justificativa; supressão indiscriminada de erros; remoção de regras ESLint ou
TypeScript apenas para passar o build; uso indiscriminado de `any`; hardcode de
credenciais; criação de soluções temporárias inseguras.

Primeiro identificar e corrigir a causa real do problema.

## 32. Alterações de segurança não podem ser feitas autonomamente

Assistentes de IA não estão autorizados a remover, flexibilizar, enfraquecer,
substituir ou ignorar estas premissas por decisão própria. Se uma tarefa conflitar
com alguma regra:

1. não executar a parte insegura;
2. informar claramente o conflito;
3. apresentar alternativa segura;
4. preservar as proteções existentes.

## 33. Auditoria antes de commits

Antes de qualquer commit relevante, verificar: arquivos staged; arquivos não
rastreados; `.env`; secrets; credenciais hardcoded; tokens; logs; referências a
IA; `Co-Authored-By`; badges/ícones de IA; alterações de dependências; mudanças no
lockfile; configurações de segurança; arquivos grandes inesperados; binários
inesperados; arquivos temporários; alterações não relacionadas à tarefa.

Em caso de dúvida sobre exposição ou alteração indevida, interromper o commit até
a situação ser avaliada.

## 34. Arquivos de governança na raiz

Manter na raiz do projeto:

- `SECURITY_RULES.md` (este arquivo) — política permanente do projeto;
- `CLAUDE.md` — obriga assistentes de IA a respeitar este documento antes de
  qualquer alteração.

## 35. Proteção dos próprios arquivos de segurança

`SECURITY_RULES.md`, `CLAUDE.md` e `.gitignore` não devem ser removidos ou
flexibilizados silenciosamente. Qualquer alteração que reduza suas proteções deve
ser previamente sinalizada. Não modificar essas regras apenas para acomodar uma
implementação.

## 36. Princípio de menor privilégio

Ao introduzir backend, banco de dados, APIs, autenticação, CI/CD, cloud ou
integrações externas, utilizar sempre o menor nível de acesso necessário. Nenhum
serviço, usuário, token ou aplicação deve possuir permissões superiores às
necessárias para sua função.

## 37. Regra final

Este projeto segue permanentemente o princípio: **falhar de forma segura em vez de
prosseguir de forma insegura.**

- Se houver dúvida entre conveniência e segurança, escolher segurança.
- Se houver dúvida se uma informação é pública ou secreta, tratá-la como secreta
  até validação.
- Se existir risco de exposição de credenciais, interromper a operação.

Nenhuma entrega, funcionalidade, prazo ou conveniência justifica violar estas
premissas.
